# tps_connector

A reference implementation of the Connector-side C ABI for the
GlobalPlatform Trusted Platform Services TPS Client API.

The crate generates a C-linkable static library and the `tpsc_connector_api.h`
header describing the `TPSCC_Connector` ABI that a Secure Component
implementation exposes to `tps_client_c`.

## `Connector`'s function-pointer fields are nullable

Every `Connector` field is `Option<unsafe extern "C" fn(...)>`, generated by
`cbindgen` as a nullable C function pointer, not a bare non-nullable one. A
malformed or partially/zero-initialized third-party connector (e.g. one
built via `memset`) can leave any field `NULL`; wrapping in `Option` lets
Rust callers `is_some()`/`ok_or`-check before invoking rather than jumping to
address 0 through a bare function pointer. `None`/`NULL` on a field means the
connector is malformed, not that the corresponding operation is
intentionally unsupported.

## Build-order dependency on `tps_client_c`

`tps_connector`'s `cbindgen.toml` sets `includes = ["tpsc_client_api.h"]`, so
the generated `tpsc_connector_api.h` `#include`s the header generated by the
`tps_client_c` crate. Cargo does not know about this relationship — building
`tps_connector` alone regenerates `tpsc_connector_api.h` without checking
that `tps_client_c/tpsc_client_api.h` exists or is up to date.

This only matters when a C toolchain compiles against both generated
headers together (`tps_connector`'s own `cargo build` only invokes
`cbindgen`, not a C compiler, so it is unaffected). If you are integrating
the generated headers into a C build, build `tps_client_c` first, or ensure
your build system regenerates both headers before compiling any C source
that includes them.

## Limitations

This code should be substantially complete and usable. It has not (yet)
been extensively statically analyzed, and as most of the code is necessarily
unsafe, this is a priority for a future version.
